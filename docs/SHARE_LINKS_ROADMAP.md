# Share links: thinking, trade-offs and what to work on next

_Written 2026-09-30, at the end of the session that designed, built, reviewed and dark-deployed v1. Companion to `docs/SHARE_LINKS.md` (how it works and how to operate it) and `docs/superpowers/specs/2026-09-30-share-links-design.md` (the decisions). This file is the "why we think what we think" plus the ordered to-do list for whoever picks it up._

## 1. What Grayson wanted (his words, condensed)
- Testing on his phone "works really well". People should be able to **record and save the animation file to a server**, get a **link**, open it on a desktop, or have it **emailed** (or texted if possible), so nobody has to save files on a phone.
- A **24-hour** window for the public link, with a **cap** so it cannot be abused.
- **Keep every animation forever** on his side ("awesome data, pull that down, we're going to look at it and do stuff with it"). Not to be a jerk about it: users get their 24 h copy.

That is two products in one feature: a convenience for the user (temporary link) and a data collection channel for Grayson (permanent archive). Almost every decision below comes from holding both at once.

## 2. The thinking behind the design

**Consent is the load-bearing decision.** A take is face landmarks (a 478-point mesh per frame, close to face geometry), hand landmarks, and optionally the person's own voice. Keeping that forever, from strangers, is the sensitive part (biometric-style data: BIPA, GDPR and similar regimes care). So: upload only on an explicit tap, never automatic; a disclosure line right beside the button says we keep a copy, what is in it, how long the link lives, and how to get it removed; the start-card copy says camera video never leaves the device and only motion and voice upload, and only on the tap. Auto-upload and a "contribute my takes" toggle were rejected: the first is hard to defend, the second is easy to forget is on. **A removal address is mandatory** and the server refuses uploads (503) until `CONTACT_EMAIL` is set, so the feature cannot go live without one. "Never delete anything" (Grayson's data policy) and "let someone remove their take" are in tension; the resolution is that the app never deletes automatically, and Grayson deletes by hand on request (see SHARE_LINKS.md for the exact steps).

**One file, two access paths.** The archive copy and the 24 h download copy are the same stored file; the link just stops resolving after the TTL (410 "expired", so people see why). Two copies would double disk for no benefit. Archive without audio was considered (less voice retention) and rejected because the voice is part of the data Grayson wants.

**The link page shows a playback preview** (Grayson chose it over a bare download). It reuses the Face Puppet renderer with no camera or MediaPipe, so it is a small chunk. Audio starts only from a tap (autoplay policy). Audio-offset sync is not done (matches in-app playback).

**Email is phase 2, link only.** Attaching the file is a bad idea (voice makes takes multi-MB, providers cap attachments) and an "email me this" form is a spam relay unless it is fixed-template, one email per take, rate-limited per IP and per address, with no user-written text. SMS was rejected (US carrier registration, cost). QR was dropped as YAGNI (it only helps desktop-to-phone; the ask was phone-to-desktop, which Copy and the share sheet cover).

**Hosting: same origin, one small container.** Caddy sends `/api/*` to a zero-dependency Node container and serves the SPA for `/t/*`; no CORS, same pattern as the other Docker apps on apps-01. Serverless/S3/R2 was rejected as a new vendor plus keys for a server Grayson already runs.

**Abuse model** (a public unauthenticated upload endpoint on a **2 GB box shared with 8 other containers**): the final review measured about 210 MB of extra memory per 50 MB upload (gzip body, inflated buffer, string, parsed JSON graph, second gzip on save), so caps are memory-driven, not just disk-driven: 50 MB per take (decompressed, so gzip bombs die), 30 uploads per IP per day, **one** concurrent upload (503 `busy`), `mem_limit: 512m`, 180 s request timeout, streamed reads, schema validation before saving, storage quota (10 GB default, 25 GB free on the box). The client IP comes from `X-Forwarded-For`, trustworthy only because the container port is loopback-only behind Caddy 2.11 with no `trusted_proxies`; the IP is stored only as a salted hash.

**Why the phase-2 and polish items are where they are.** Everything not needed to be safe and honest at launch was deferred; the reviewers' deferred list is in section 4.

## 3. What the review process taught us (so the next reviewer does not rediscover it)
- The per-task reviews all passed; the **whole-branch review found the Critical** (memory exhaustion) because it looked across tasks and measured. Measure resource cost of public endpoints; do not reason about it.
- **Remount bugs are invisible to unit checks:** the phone layout and the desktop layout mount different copies of the controls, so rotating a phone reset the Save state and let a second tap archive a duplicate voice recording. State that must survive a layout switch lives above it (`hooks/useSaveLink.ts` in FaceDemo).
- **Copy is a spec item.** The start-card wording was wrong once ("video and voice stay on this device" became false the moment upload existed). A regex in `scripts/phone-check.mjs` guards the phrase; change both together.
- The e2e gate (`npm run share-check`) is worth its runtime: it caught real bugs, and it proves the phone Save flow plus rotation in WebKit. It is flaky only when the machine is short of RAM (kill stray node/vite first).

## 4. What to work on next (ordered)

1. **Turn it on and prove it live (small, needs Grayson).** Choose the public removal address, set `CONTACT_EMAIL` in `/home/grayson/apps/mocap-api/.env.local` on the box, `sudo docker compose up -d --force-recreate`. Then do one real save, open the link on a phone, download it, and watch `sudo docker stats --no-stream` during a genuinely large take (the 512 MB limit and one-slot default are reasoned, not measured on the box). If a real 2-minute take is refused (the 50 MB cap is about 150 s at most for a synthetic take; real frames are heavier), decide: raise the cap plus `mem_limit` (about 1g) and `MAX_CONCURRENT_UPLOADS=2`, or thin the frames (fewer decimals, drop unused blendshapes) in the recording schema.
2. **Get the data off the box and backed up.** The VPS holds the only copy until pulled. `MOCAP_ADMIN_TOKEN` is not set on Grayson's PC (he reads it from `.env.local` on the box himself; never paste it into chat). Run `scripts/Pull-Takes.ps1` by hand once, then decide on a nightly scheduled task (offer, do not silently create). Also point a V: backup at `Tool-PuppeteerLab\data\takes` (the nightly backup-ops sweep covers project folders under `C:\Projects-local`, so it will pick `data\` up automatically once it exists; confirm it is not excluded).
3. **A real-phone run** (nothing has run on a real phone yet): the start card, one permission prompt, Record without a prompt, backgrounding, plus the new things: Save & get link, Copy (clipboard permission on iOS), the share sheet, the link page on the phone, the audio-only-on-tap behaviour (and whether iOS Safari decodes a `audio/webm;codecs=opus` take recorded in Chrome; if not, the viewer needs a fallback or a note).
4. **Use the data (this is what the archive is for).** Nothing reads the archive yet beyond the pull. Ideas: a small script that summarises takes (duration, frames, hasAudio, channels, blendshape ranges); a local "take browser" that replays pulled takes with the same renderer; feed takes to `tools/blender_import_recording.py` (the v3 Blender importer already exists); look at what people actually do (blendshape usage, hands vs face) before deciding what to build next. Keep the consent line honest as uses grow: if takes are ever used beyond "Grayson looks at them", say so in the disclosure.
5. **Phase 2: email the link.** Resend, link only, fixed template, rate limits per IP and per address, no stored address beyond an `emailed` flag. Needs an account, a verified sender on graysonchalmers.com (DNS records), and an API key in `.env.local` (Grayson pastes). Plan it as its own small plan (`POST /api/takes/:id/email`, a field in `SaveLink`); do not build it before item 1 is live.
6. **Link previews for sharing.** When someone texts the link, the card shows nothing useful. Serving Open Graph tags and a thumbnail for `/t/<id>` (the server would need to render or store a poster frame) would make shared links look like a product. Optional; think about it once real links are being shared.
7. **Extend Save to the other four demos** (they use the shared `RecorderControls` `footer` slot and produce the same v3 schema for hand demos; only Face Puppet is phone-verified). Also update the Web-GC portfolio card copy only after phones are verified.
8. **Hardening backlog (deferred by reviewers, none blocks launch):** persist the rate limiter (an in-memory reset on restart lets one IP crash-and-repeat if anything ever OOMs); bucket IPv6 by /64 if an AAAA record is ever added; do not spend the daily slot on failed attempts; SIGTERM force-exit timeout; orphan `.gz` files after a crash and the quota cache not seeing external files (restart after hand deletes); alert on disk and quota (today only a log line `[mocap] storage quota reached`); the Download button re-fetches the take (could reuse the loaded JSON; after expiry it downloads a 410); the viewer keeps the base64 audio in state, ignores devicePixelRatio and re-renders every 100 ms while paused; aria labels and `role="alert"` on the link box and error text; a shorter or cheaper Docker HEALTHCHECK on `/api/health`; the read-only URL input is 11 px and could zoom on iOS focus (rejected as a blocker because `index.html` sets `maximum-scale=1`; recheck on a real phone).
9. **The older phone polish bundle** (unchanged): `inert` on the closed drawer, visible face counting as activity for idle pause, a 390x667 short-viewport case in `phone-check`, phone defaults from real fps, and make phone-check's fixed-wait checks (drawer 400 ms, Turn on 500 ms) wait for the condition (they flake under load).

## 5. Traps and facts to remember
- apps-01: host port **3017** (3016 has other listeners), container `mocap-api-mocap-api-1`, app dir `/home/grayson/apps/mocap-api`, data bind mount `/home/grayson/mocap-data` (must be owned by uid 1000 or every save returns 500), Caddy `handle /api/*` (not `handle_path`), Caddyfile backup `Caddyfile.bak-20260930092939`. Update the API by piping `git archive --format=tar HEAD:server` over ssh into the app dir and `sudo docker compose up -d --build` (keeps `.env.local`).
- `PORT` and `DATA_DIR` are fixed in compose; do not set them in `.env.local`. Local `npm run server` writes `./data`, which is also `Pull-Takes.ps1`'s default destination: use a different `DATA_DIR` for local testing.
- Removing a take on request: delete `<id>.json.gz` and `<id>.meta.json` on the box (and the pulled `data/takes/<id>.json` here), then restart the container.
- The static site and the API deploy separately: a static redeploy does not touch the container and vice versa.
- Dev: `npm run dev` proxies `/api` to `127.0.0.1:8787` (override with `MOCAP_API`); with no API the Save button simply hides.
