# 😈 Teardown: Puppeteer Lab (2026-09-06)

Second teardown. The first (2026-09-04) found the broken exports and the Gemini bundle leak and named the DebugView fusion as the biggest structural debt; all of that landed the same day. This one runs against a goal Grayson stated explicitly today, which the repo had never written down:

> This is a **test bed and a demo for game-dev friends**: "look, you can run motion capture on your hands with a webcam, use it to control other objects, and save it out."

That reframing is the main lens change. Most findings below measure how far the tree is from *that*, not from the product pitch in the old `PLANNING.md`. The goal now lives in [NORTH_STAR.md](../NORTH_STAR.md) and [ADR-0001](adr/0001-demo-first-test-bed.md).

Ground rules followed: every finding cites a file and line; each major component got a steelman before the swing; defect and taste are labeled separately; past-Claude's work from 2026-09-04 gets zero deference.

---

## 🎯 The Rebuild Question

**If Puppeteer Lab vanished and we built it today for that goal, what would we build?**

A thin **tracking core** that emits one frame type for hands and face (pose later). A **recorder** that taps that frame no matter which demo is open. An **export** with a documented schema that opens in one real tool (Blender first, because a 60-line `bpy` script gets you there). A handful of **thin demos**, each showing one way to consume the frame, arranged as a five-stop tour:

1. **Hand Telemetry**: "this is what the camera sees" (skeleton, confidence, distances).
2. **Air Canvas**: "drive a 2D thing" (pinch to draw, grab to move).
3. **Tempo Strike**: "drive 3D things inside a real game loop" (hands are sabers).
4. **Motion Recorder**: "record it, scrub it, export it, open it in Blender."
5. **Face Puppet**: "same pattern, different model."

It would run **offline** (vendored WASM, models, CSS, audio) because friend-demos happen on other people's wifi. It would have a GIF at the top of the README. It would deliberately omit MIDI/OSC, BVH, WebRTC collaboration, Spatial Pong, and every roadmap item nobody has asked for.

**Headline diff vs. reality:**

- The "shared engine" from 2026-09-04 covers **2 of 5** demos. Hand data exists in **two incompatible shapes** (a smoothed world-space fingertip vs. raw 21-point landmarks), and the smoothing control is wired to the shape the drawing demos never read.
- The recorder is **demo-shaped** (HAND vs FACE, different fields per caller), has **no schema doc**, and **no importer** for any tool it names. "Export for Blender/Maya/Unity" is a JSON dump.
- Docs describe a **product** ("framework for games and media", "Four Core Demos" when there are five), not a test bed. Per-demo roadmaps are AI-generated wish lists.
- Runtime depends on **four CDNs** (Tailwind play CDN, MediaPipe WASM, MediaPipe models, a codeskulptor demo song).
- **Motion Recorder is the most on-mission demo and the least developed**: no live trail, no scrubber, two spheres instead of a hand.

The core is sound. This is a "keep the core, fix three lies on the demo surface, then converge the data model" teardown, not a demolition.

## 🔍 Findings by lens

Ranked by severity across lenses. Effort: **S** = one session or less, **M** = two or three sessions, **L** = four or more.

### 🔴 Actively costing

**F1. Air Canvas's "Global Smoothing" slider does nothing.** (Red team, Architect)
Evidence: [components/aircanvas/AirCanvas.tsx:47](../components/aircanvas/AirCanvas.tsx) destructures only `lastResultsRef` and `setSmoothingFactor` from `useMediaPipe`; its `drawFrame` reads `lastResultsRef.current.landmarks`, which is raw MediaPipe output. `setSmoothingFactor` writes `settingsRef.current.smoothingFactor` ([hooks/useMediaPipe.ts:52](../hooks/useMediaPipe.ts)), and that value is applied only at lines 177-196, to `handPositionsRef` (the world-space fingertip), a ref Air Canvas never touches. The slider, its four presets, the shared `SmoothingControl`, the `smoothingToLerp` math and its two tests all pass while the drawn line is unaffected. Hand Telemetry is half-dead the same way: the drawn skeleton is raw; only the sidebar numbers smooth.
Steelman: the slider was inherited from DebugView and last session's extraction was byte-identical, so nothing regressed. True, and it was already dead in DebugView; nobody had a camera to notice.
Cost: a friend drags the slider and asks what it does. **Fix: S.** Apply smoothing at the landmark level inside `useMediaPipe`. This is also phase 1 of [TDD-001](tdd/TDD-001-tracker-core.md).

**F2. The hub promises a "3D Timeline Scrubber" that does not exist.** (Maintainer, Newcomer)
Evidence: [components/DemoHub.tsx:436](../components/DemoHub.tsx) ("Orbit, pan, and scrub through takes with synced audio"). The old `PLANNING.md`, `demos/motion-recorder/PLANNING.md`, and `HANDOFF.md`'s current-state paragraph repeat it. [hooks/useRecorder.ts:190](../hooks/useRecorder.ts) defines `seekPlayback`; a repo-wide grep finds no caller. `RecorderControls.tsx` exposes Record, Stop, Play, Export, Load. Playback loops; you cannot scrub.
Cost: a false claim on the demo's front door. **Fix: S.** One range input bound to `seekPlayback`; see [TDD-003](tdd/TDD-003-motion-recorder-upgrade.md).

**F3. The North Star on disk was marketing copy, not the goal.** (Maintainer)
Evidence: the old `PLANNING.md` North Star read "a zero-hardware spatial tracking and recording framework for games and media... enables developers and creators to control games, sketch in spatial air, puppeteer 3D characters." README led with the same pitch. Both said "The Four Core Demos"; the hub has five. Nothing on disk said "test bed", "demo", or named an audience. The 2026-09-04 sessions optimized against a product target and it shows in what got polish (Telemetry: eight toggles, a synth, a hologram cube) versus what did not (the recorder).
Cost: every future session re-derives the goal or drifts. **Fixed this session:** `NORTH_STAR.md`, ADR-0001, `PLANNING.md` rewritten as the roadmap.

### 🟡 Will cost soon

**F4. Two copy-pasted tracker hooks; the engine covers 2 of 5 demos.** (Architect)
Evidence: [hooks/useMediaPipe.ts:70-130](../hooks/useMediaPipe.ts) and [hooks/useFaceTracker.ts:20-90](../hooks/useFaceTracker.ts) share FilesetResolver init, `startCamera`, `predictWebcam`, and cleanup almost line for line; they differ in landmarker class and options. Tempo Strike and Motion Recorder draw through [components/WebcamPreview.tsx](../components/WebcamPreview.tsx), which has its own rAF loop and its own `HAND_CONNECTIONS` table (lines 16-23) that differs from [components/telemetry/drawingHelpers.ts:34-40](../components/telemetry/drawingHelpers.ts). [components/FaceDemo.tsx:40-140](../components/FaceDemo.tsx) is a third hand-rolled rAF loop. A third modality (pose) would be a third copy.
Steelman: each hook is small and readable; duplication is cheaper than a premature abstraction. Fair for two. The "drive a puppet with hands *and* face" demo that the North Star implies needs both in one camera, one loop, one frame; the current shape makes that two camera grants and two rAF loops.
Cost: the first hands+face demo, or the first pose experiment. **Fix: M**, [TDD-001](tdd/TDD-001-tracker-core.md).

**F5. Runtime depends on four CDNs.** (Red team)
Evidence: [index.html:10](../index.html) loads the Tailwind play CDN (which warns "not for production" and re-JITs on every page load); `useMediaPipe.ts:79,86` and `useFaceTracker.ts:25,32` fetch WASM from jsdelivr and roughly 12 MB of models from `storage.googleapis.com`; [constants.ts:27](../constants.ts) streams the Tempo Strike song from a codeskulptor demo bucket. `dist/` is otherwise fully static. A blocked CDN or captive-portal wifi leaves every demo at "Starting Camera Tracking..." with no useful error.
Cost: the first demo on someone else's network. **Fix: S to M**, [TDD-004](tdd/TDD-004-offline-first-assets.md).

**F6. Camera-rate React state updates in two demos.** (Red team)
Evidence: [components/telemetry/HandTelemetry.tsx:245-257](../components/telemetry/HandTelemetry.tsx) calls `setMetrics` with a fresh object every frame; [components/FaceDemo.tsx:585](../components/FaceDemo.tsx) calls `setBlendshapes` every frame. Both re-render their whole sidebar at camera rate, the exact anti-pattern the README's Technical Guide warns against.
Cost: jank in the demo whose point is smoothness, and main-thread time stolen from MediaPipe. **Fix: S.** Throttle to about 10 Hz, or move the readout into a small component that reads a ref on its own interval.

**F7. Face recordings will produce 40 MB+ JSON and freeze the tab on export.** (Red team)
Evidence: [components/FaceDemo.tsx:546-551](../components/FaceDemo.tsx) captures all 478 landmarks plus 52 blendshapes per frame; the full export in [hooks/useRecorder.ts](../hooks/useRecorder.ts) does `JSON.stringify(session, null, 2)` on the main thread (pretty-printed, one number per line) and inlines base64 audio. Twenty seconds at 60 fps is about 1.7 million numbers.
Cost: "Performance Replay" export hangs or crashes on a real take. **Fix: S to M**, [TDD-002](tdd/TDD-002-recording-schema-and-export.md) (compact schema, unpretty JSON, off-main-thread serialization).

**F8. Motion Recorder is the on-mission demo and the weakest one.** (Economist)
Evidence: [components/MotionRecorder.tsx:107-152](../components/MotionRecorder.tsx) contains commented-out design notes admitting the trail cannot be drawn during recording because the buffer is private to the hook; the replay shows two spheres, not a hand; recording captures only the fingertip (`captureFrame({leftHand, rightHand})` at line 128), so the "mocap" export is two points per frame. Hand Telemetry (about 950 lines) records all 21 landmarks per hand but is positioned as a diagnostic.
Steelman: two spheres are honest about what the world-space API provides today, and the 3D replay with orbit is genuinely useful for judging depth. Yes, and it still fails the North Star's third verb ("save it out and use it") on first contact.
Cost: the least convincing stop on the tour is the one that matters most. **Fix: M**, [TDD-003](tdd/TDD-003-motion-recorder-upgrade.md).

**F9. Export format is undocumented and has no consumer.** (Maintainer)
Evidence: `useRecorder.ts` emits three formats (`"2.0"`, `"2.0-kinematics"`, audio webm); `types.ts` `FrameData` has five optional fields and nothing says which demo fills which; the kinematics export hard-codes `fps: 60` instead of measuring it; there is no importer for any tool the hub names. A friend who asks "can I use this in Unity?" gets a JSON to parse themselves.
Cost: export stays a checkbox until one real tool opens it. **Fix: M**, [TDD-002](tdd/TDD-002-recording-schema-and-export.md) (schema doc, versioned envelope, a Blender import script).

**F10. Stale demo docs.** (Maintainer)
Evidence: `demos/motion-recorder/README.md` said "Entry Point: MotionRecorder.tsx (To be created)", "Data Export: (Planned)", "Scrub: (Planned)", and referred to "the Data Visualizer" (deleted 2026-09-04). [components/aircanvas/lineReliability.ts:9-10](../components/aircanvas/lineReliability.ts) says the capture loop "lives in DebugView" (deleted). README and PLANNING said four demos.
**Fixed this session:** the README and PLANNING files. The code comment is on the next code session's list.

**F11. No LICENSE file, but every source file carries an Apache-2.0 SPDX header.** (Newcomer)
Evidence: `git ls-files | grep -i licen` returns nothing; every `.ts`/`.tsx` starts with `SPDX-License-Identifier: Apache-2.0` (AI Studio boilerplate). The repo is public.
Cost: a friend who wants to lift the tracker core has no grant to rely on. **Fix: S.** Add `LICENSE` (Apache-2.0 matches the headers; MIT is fine too if the headers are stripped).

### 🔵 Taste, labeled as such

**F12. The `types.ts` JSX `any` catch-all is dead weight.** With the entire `declare global { namespace JSX ... }` block removed, `tsc --noEmit` exits 0 (verified 2026-09-06, file restored). `@react-three/fiber` v8 already types these elements. The `[elemName: string]: any` index signature makes every unknown JSX tag legal, which hides typos. 🪦 Kill; **S**.

**F13. Three naming systems for five things.** AppMode ids (`game`, `aircanvas`, `telemetry`, `recorder`, `face`), component files (`RhythmGame`, `AirCanvas`, `HandTelemetry`, `MotionRecorder`, `FaceDemo`), and `demos/` doc folders (`tempo-strike`, `air-canvas`, `hand-telemetry`, `motion-recorder`, `face-telemetry`). The Tempo Strike hub card is titled "Games". `demos/` looks like code and holds only markdown; Tempo Strike's four files sit loose in `components/` beside shared widgets. Fix is a pure rename, **S**, and should come **last** in the migration (after behavior stabilizes) so moves do not tangle with real diffs.

**F14. Per-demo `PLANNING.md` roadmaps are aspirational AI output.** MIDI/OSC remapper, BVH/GLTF/CSV transposer, Spatial Pong, Marionette IK, Cybernetic Mimic Mask, collaborative WebRTC canvas. None serve the stated goal yet, and together they make the project read as five products. Kept on disk as an idea backlog; the root `PLANNING.md` now says explicitly that they are not commitments.

**F15. `DEMO_CHART` is a mutable module singleton** ([constants.ts:85](../constants.ts)) whose `hit`/`missed` flags are mutated in place by `GameScene` and reset by `RhythmGame.startGame`. Works today; bites the moment a second chart or a difficulty selector exists.

**F16. Steelmans that survived, recorded so nobody re-litigates them.** *Tempo Strike* is about 15% of the codebase for a game that is not "mocap", but it is the strongest "control other objects" proof and it consumes exactly the world-space API a game dev would want: keep, freeze scope. *Hand Telemetry*'s synth and hologram are polish on a rarely used surface, but the diagnostic view is what makes the tracking legible to a skeptical friend: keep, stop growing. *`docs/superpowers/`* spec and plan are history worth keeping. *CI + smoke* earn their keep every push.

## 🏗️ The v2 sketch

Target shape (folder names are proposals; the point is the layering):

```
core/
  tracker/     camera + landmarker lifecycle: one getUserMedia, one rAF, hands + face (+ pose later)
  signal/      resolveHands, landmark-level smoothing, gestures, world mapping
  recorder/    useRecorder over TrackedFrame; schema v3; exporters (json, kinematics, audio, glTF later)
  render/      useHandRenderLoop + one skeleton/landmark drawer
demos/
  hand-telemetry/   code + README (today: components/telemetry + demos/hand-telemetry)
  air-canvas/       code + README
  tempo-strike/     code + README (today: four loose files in components/)
  motion-recorder/  code + README
  face-puppet/      code + README
tools/
  blender_import_recording.py    opens a recording as keyframed empties (TDD-002)
public/mediapipe/                vendored wasm + models (TDD-004)
docs/  NORTH_STAR.md (root), PLANNING.md (root), tdd/, adr/, TEARDOWN-*.md
```

**Carries over as-is:** every pure module (`resolveHands`, `gestureAnalysis`, `smoothing`, `lineReliability`, `pinchTracer`, `drawingHelpers`, `FaceMeshRenderer`), all five demo UIs, `useHandRenderLoop`, CI + smoke, the hub.

**Migration order** (each step leaves the app working and the gates green):

1. Landmark-level smoothing inside `useMediaPipe` (F1). One test.
2. Introduce `TrackedFrame` behind the existing `handPositionsRef` / `lastResultsRef` API so no consumer changes yet. Adapter, not rewrite.
3. Fold face into the tracker (second landmarker on the same loop); `FaceDemo` moves onto `useHandRenderLoop`.
4. Recorder over `TrackedFrame`; schema v3; compact export; Blender import script.
5. Motion Recorder upgrade: exposed buffer trail, scrubber, skeleton replay.
6. Vendor assets; add the "no CDN in dist" smoke probe.
7. Folder moves and naming unification, last, as a pure rename commit.

Executing steps 2 through 5 is a `phased-rebuild`; each TDD carries its own gates.

## ▶️ The one change worth making first

**Fix F1: make smoothing act on the landmarks every demo draws.** About 40 lines in `hooks/useMediaPipe.ts` (lerp each of the 21 landmarks against the previous frame's same-side landmarks before publishing `lastResultsRef`, using the slider's factor) plus one pure test on the lerp step. It removes a demo-visible lie, gives Air Canvas and Hand Telemetry a control that visibly works, and is step 1 of TDD-001, so nothing is thrown away later. One session, best clarity per hour in the repo.

Alternatives, with tradeoffs:

- **Vendor the assets first (TDD-004).** Pick this if a demo date is inside two weeks. It de-risks the whole show rather than one slider, and it is independent of the data-model work. Costs about the same; buys less architectural progress.
- **Wire the scrubber first (TDD-003, step 1).** `seekPlayback` already exists; a range input and a pause-on-scrub rule is an hour. Kills F2 and improves the on-mission demo. Pick this if you want a visible win before the refactor. It does not move the data model.

Do not start with the folder moves (F13). Renames before behavior stabilizes are how the naming chaos happened last time.
